## 3. 优先修复：所有恢复路径使用同一订单验证规则

**已复现的客户端缺口。** 旧版 `main.py` 的 `book_slot()` 在写请求超时或收到“已有预约”等提示后，调用 `covered_booking()`，随后直接 `verify(existing['id'])`。这里没有传入预期时段、时长、座位，也没有再次检查四楼允许池。正常新单则走 `verify(id, begin, duration, seat_id)`。入口 `reserve_day()` 对已有单虽然检查四楼允许池，但仍只按列表时间判断覆盖，未重新核对详情时段覆盖。新版参考快照中仍可见对应恢复分支。

离线模拟：候选为四楼座位，写请求抛出 `requests.Timeout`；查单列表返回覆盖目标时段的订单，详情返回二楼西座位。当前 `book_slot()` 会接受并返回该结果。模拟完全使用假响应，不证明现实中已经产生过这样的错误订单。

改进建议：抽出统一验证入口，区分两种契约。

1. **本次新单**：服务端明确确认，详情核对用户、有效状态、精确开始时间、时长、具体座位和允许池。
2. **已有覆盖单／超时恢复单**：详情重新验证用户、有效状态、时段确实覆盖目标、房间和允许池。覆盖单可以更长，不能错误地一律要求与目标开始及持续时间完全相等。

结果至少区分 `confirmed_new`、`already_covered`、`uncertain`、`failed`。恢复查到一个合法订单，不自动等于证明本次请求创建了它。查不到也不等于证明未成交，应有有限的确认流程和明确停止条件。

验收：其他楼层、错误所有者、已取消订单、列表与详情时段不一致必须拒绝；合法的更长覆盖订单仍接受；超时未确认时不得紧接着提交另一个座位。首次成功、重复响应和超时恢复走同一个最终允许池检查。

## 4. 优先明确：本地、两个仓库之间没有共享互斥

**已确认的架构边界。** `run.lock` 和 `.local/daily-state-*.json` 只在当前文件系统内生效。GitHub 并发组作用于所在仓库，不能靠同名组把另一个仓库和 Windows 本机也锁住。新版 `scheduled-selftest.yml` 还使用不同于正式任务的并发组，因此它与正式任务也可能同时运行。

“提交前查单”存在两个执行端同时查到无订单的竞态，不能据此宣称全局只提交一次。学校是否会原子拒绝重复订单，需要独立证据；本轮没有对学校制造并发请求。

建议后续确定一个主预约执行端，其余作为只读验证或显式接管的备用端；如果确需多端自动接管，应设计可原子获取、有期限和所有者校验的共享租约。即使使用租约也需处理过期、恢复与订单未知状态，不能仅凭一个锁宣称严格一次。

验收：离线模拟两个执行端同时通过查单的反例；检查每个真实写入入口的租约/主端规则；学校端去重能力单列证据。用户目前已授权全部启用，本次没有擅自关闭任何一端。

## 5. 满座、超时与重启状态需要更精确的语义

### 5.1 满座是地图业务结论，不是空列表的同义词

旧版 `available_seats()` 只要看到至少一个允许 ID，就允许返回空候选。离线构造“允许池有两个座位，响应只带一个占用座位”的地图，会被 `book_fourth_floor()` 判为 `NoSeats`，旧版随后结束整天计划。

这是**已复现的客户端判断路径、实际影响待验证**：还不能断言学校真实接口会返回这种部分图。需先保留脱敏的响应结构并核对接口的完整性、分页、房间与时段语义。只有完整、正确且适用目标时段的地图才支持终态满座。缺失、异常或暂未生效应标为未知；允许有限复查，避免无限轮询。

新版已让首轮 `NoSeats` 继续下一轮，值得借鉴；这并没有自动解决后续轮次的完整性判断。

### 5.2 超时优化先保护正确性，再追求速度

新版 `0499556` 已把受预算限制的预约/搜索请求读超时上限从 15 秒调整为 6 秒，增加双次预热与 1/2/3 秒开放边界退避。**当前代码仍保留写超时先查单**，不能把它描述成已经盲目换座。

Codex 不采纳“写请求超时后立即换座”的建议。可以分别调整只读请求、写请求和查单确认预算，但需要以实际延迟与未知成交率验证。Requests 的连接/读取超时不是总墙钟时限；旧版仅对 `bookSeats` / `searchSeats` 施加轮次预算，登录、分类和查单不都在该预算内。因此“截止后不再新增预约请求”比“全流程严格 20 秒结束”更准确。[Requests 官方说明](https://requests.readthedocs.io/en/latest/user/advanced/#timeouts)

### 5.3 当日状态文件缺少预约意图标识

旧版状态文件按执行日期命名，只记录已尝试轮次和结束原因，没有绑定目标日期、时段、允许池或配置摘要。当天配置改变后重启，可能直接沿用旧的 `finished`。轮次在准备和提交前就写入 `attempted`，崩溃后有“未实际提交却被当作已执行”的取舍。

建议状态关联预约意图，并记录准备中、已提交待确认、已确认等阶段。恢复前先查单；不能通过删状态文件来无条件重跑写入。验收需覆盖配置变更、提交前崩溃、提交后未落盘和损坏状态文件。

## 6. 对 DeepSeek 交接意见的纠正与保留

1. **“频繁修改 workflow 会重置调度注册，须冷却几小时”目前是未证实假设。** 固定配置观察有助于减少变量，但官方材料没有为本案给出重置机制或冷却时长，不能用约 3.4 小时、6 小时的观察反推出内部机制。也不能保证冻结 24 小时一定恢复。[GitHub schedule 文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)
2. **`cancel-in-progress: false` 不等于所有触发无限排队。** 两个仓库当前配置未指定 `queue`；默认同组最多一个运行、一个等待，新等待替换旧等待。既不能保证每次触发都保留，也不提供跨仓库互斥。[GitHub 并发文档](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)
3. **外部定时调用成功不是预约成功。** 固定并记录实际 API 版本，按对应响应解析，再关联真正的运行。交接示例使用 `2022-11-28`，当前官方 `2026-03-10` 文档为 `200` 并返回运行 ID；不能硬编码“只有 204 才算成功”。验证链应为请求被接受 → 运行事件/版本/目标正确 → 业务结果已核验。测试外部链路优先用只读模式，不额外创建测试预约。[GitHub dispatch 文档](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)
4. **最小权限建议可取，权限用途需准确。** 外部触发用仅授权目标仓库的 fine-grained PAT，`Actions: write`；工作流 `checkout` 使用自身 `GITHUB_TOKEN` 的读取权限，不因此要求把外部 PAT 的权限扩大。第三方中转同样不能承诺端到端准点。
5. **定时探测默认应无副作用。** 旧测试有固定日期和首次启动自禁用保护，但仍会尝试真实预约、并共享正式并发组；新版自测试也有真实预约。建议后续将时间戳探针与真实新单验收分开，后者明确日期、失效条件及互斥。当前开关按用户要求保留。
6. **签到提示的方向合理，时间窗需有来源。** 新版新增的固定“开始前后各 30 分钟”提示应以学校当前规则或订单页面核对，不把代码中的常量当作已经验证的校方规则。
